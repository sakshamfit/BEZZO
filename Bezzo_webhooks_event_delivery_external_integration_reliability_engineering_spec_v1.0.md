# Bezzo Webhooks, Event Delivery & External Integration Reliability Engineering Specification v1.0

**Product:** Bezzo  
**Document Type:** Engineering Specification  
**Version:** 1.0  
**Status:** Implementation Baseline  
**Scope:** Webhooks, domain-event delivery, external integrations, reliability, security, observability, replay, and operational tooling

---

## 1. Purpose

This specification defines the engineering design for reliable event delivery in Bezzo.

It covers:

- outbound webhooks
- inbound webhooks
- internal domain-event delivery
- event envelopes and versioning
- subscription management
- signing and authentication
- retries and backoff
- idempotency and deduplication
- ordering
- dead-letter handling
- replay
- delivery tracking
- endpoint health
- external provider integrations
- security controls
- observability
- disaster recovery
- implementation standards

The design must support Bezzo's marketplace model while preventing external integration failures from corrupting core order, payment, inventory, logistics, or supplier workflows.

---

# 2. Reliability Objectives

Event delivery must be treated as an asynchronous reliability boundary.

Core principles:

1. A committed business transaction must not depend on an external webhook receiver being available.
2. Event delivery must be retryable.
3. Consumers must be able to safely process the same event more than once.
4. Events must have globally unique identifiers.
5. Delivery attempts must be observable.
6. Failed deliveries must become operationally recoverable.
7. External integrations must not receive another tenant's data.
8. Secrets must never be exposed in logs.
9. Webhook endpoints must be protected against SSRF and abuse.
10. Event schemas must evolve without unexpectedly breaking consumers.
11. Replay must be controlled and auditable.
12. Provider outages must degrade asynchronous integration behavior without unnecessarily blocking core Bezzo operations.

# 4. Inbound vs Outbound Webhooks

## 4.1 Outbound Webhooks

Bezzo sends events to an external subscriber.

Examples:

- supplier ERP integration
- supplier POS system
- buyer enterprise integration
- partner integration
- approved business automation system

Outbound delivery is asynchronous.

The originating business transaction must not wait for successful external delivery.

## 4.2 Inbound Webhooks

An external provider calls Bezzo.

Examples:

- payment gateway payment status
- payment refund status
- Porter delivery status
- notification provider callback
- approved ERP/POS integration

Inbound requests must be:

1. authenticated
2. signature-verified where supported
3. schema-validated
4. deduplicated
5. persisted when required
6. acknowledged quickly
7. processed asynchronously where possible

# 5. Event Envelope

All Bezzo platform events should use a common envelope.

Example:

```json
{
  "event_id": "evt_01JXXXXXXXXXXXX",
  "event_type": "order.created",
  "event_version": 1,
  "occurred_at": "2026-01-15T10:20:30.000Z",
  "tenant_id": "tenant_123",
  "actor_id": "user_456",
  "correlation_id": "req_789",
  "causation_id": "evt_previous",
  "aggregate_type": "order",
  "aggregate_id": "ord_123",
  "ordering_key": "order:ord_123",
  "source": "orders",
  "data": {}
}
```

Required fields:

- `event_id`
- `event_type`
- `event_version`
- `occurred_at`
- `tenant_id` where tenant context applies
- `correlation_id`
- `aggregate_type`
- `aggregate_id`
- `source`
- `data`

Recommended fields:

- `actor_id`
- `causation_id`
- `ordering_key`
- `metadata`

# 6. Event IDs

Every event must receive a unique immutable identifier.

Requirements:

- generated by Bezzo
- globally unique
- never reused
- retained for deduplication and audit
- included in outbound requests
- included in logs and tracing

Recommended format:

```text
evt_<unique-id>
```

Consumers must use `event_id` as one of the primary deduplication keys.

---

# 7. Correlation and Causation

## 7.1 Correlation ID

A correlation ID connects operations belonging to the same request or business flow.

Example:

```text
buyer checkout
    ↓
order created
    ↓
payment initiated
    ↓
payment confirmed
    ↓
supplier fulfillment
    ↓
delivery
```

A common correlation ID allows operators to trace the complete flow.

## 7.2 Causation ID

`causation_id` identifies the event or operation that directly caused the current event.

This is useful for:

- debugging
- audit analysis
- event-chain tracing
- incident investigation

# 8. Transactional Outbox

Business events must be written transactionally with the business state change whenever practical.

Example:

```text
BEGIN

UPDATE orders
SET status = 'CONFIRMED'

INSERT INTO outbox_events (...)

COMMIT
```

If the transaction commits, the event exists.

If the transaction rolls back, the event does not exist.

This prevents:

```text
Database updated
       +
Event publishing failed
       =
Missing integration event
```

The outbox worker later publishes pending events.

- subscriber
- endpoint
- subscribed event types
- filtering rules
- secret
- status
- retry policy
- delivery limits
- created/updated timestamps

Example:

```text
Supplier
  └── Integration
       └── Webhook Endpoint
            ├── order.created
            ├── order.confirmed
            ├── fulfillment.created
            └── inventory.updated
```

# 12. Endpoint Registration

Endpoint registration must validate:

1. URL syntax
2. HTTPS requirement
3. allowed ports
4. DNS resolution policy
5. private-network restrictions
6. hostname/IP restrictions
7. webhook ownership
8. event subscription permissions

Production outbound webhooks should use HTTPS.

HTTP may be permitted only in controlled local development environments.

---

# 13. SSRF Protection

Outbound webhook delivery creates an SSRF risk.

Bezzo must prevent requests to:

- localhost
- loopback addresses
- private IPv4 ranges
- private IPv6 ranges
- link-local addresses
- cloud metadata endpoints
- internal service hostnames
- internal DNS targets
- restricted network ranges

Validation must occur both:

1. when the endpoint is registered
2. immediately before connection where DNS resolution is involved

DNS rebinding must be considered.

Redirects should be disabled by default.

If redirects are ever supported, every destination must undergo the same validation.

---

# 14. Webhook Signing

Bezzo outbound webhooks should use HMAC signing.

Example conceptual header:

```text
X-Bezzo-Signature: t=timestamp,v1=signature
```

The signed message should include:

```text
timestamp + "." + raw_request_body
```

Recommended algorithm:

```text
HMAC-SHA256
```

Consumers should:

1. retrieve the configured secret
2. read the raw request body
3. reconstruct the signed payload
4. calculate the expected signature
5. compare using constant-time comparison
6. validate timestamp tolerance
7. reject invalid or stale signatures

---

# 15. Secret Management

Webhook secrets must:

- be generated cryptographically securely
- never be stored in plaintext when avoidable
- never appear in application logs
- never appear in analytics events
- never be included in error responses
- support rotation
- support controlled overlap during rotation

Recommended rotation model:

```text
OLD SECRET
    +
NEW SECRET
    ↓
accept both temporarily
    ↓
consumer confirms migration
    ↓
revoke old secret
```

---

# 16. Subscription Security

A subscriber must only be allowed to subscribe to events it is authorized to receive.

Example:

A supplier integration may receive:

```text
inventory-related events
supplier order events
supplier fulfillment events
```

It must not receive:

```text
another supplier's private data
platform-wide administrative events
unrelated buyer private information
internal security events
```

Authorization must be checked server-side.

---

# 17. Event Filtering

Subscriptions may optionally define filters.

Example:

```json
{
  "event_type": "order.updated",
  "filters": {
    "supplier_id": "sup_123"
  }
}
```

Filtering must occur before payload delivery.

The filter engine must not allow a subscriber to bypass tenant authorization.

# 18. Delivery Attempts

Each webhook delivery creates a delivery attempt record.

Recommended fields:

- delivery ID
- event ID
- subscription ID
- endpoint ID
- attempt number
- started timestamp
- completed timestamp
- HTTP status
- network error
- response latency
- response size
- next retry time
- final status

Sensitive response bodies should be redacted or truncated.

---

# 19. Timeout Policy

Outbound webhook requests must have strict timeouts.

Suggested baseline:

```text
connection timeout: short
request timeout: configurable
maximum total request duration: bounded
```

The exact production value should be load-tested and configured centrally.

A slow endpoint must not consume unlimited worker capacity.


# 21. Retry Strategy

Retries must use exponential backoff with jitter.

Conceptual schedule:

```text
attempt 1 → immediate
attempt 2 → short delay
attempt 3 → larger delay
attempt 4 → larger delay
...
```

Use:

```text
delay = min(max_delay, base_delay × 2^attempt) + jitter
```

Jitter prevents many failed endpoints from causing synchronized retry spikes.

Maximum attempts and maximum retry duration must be configurable by integration type.

---

# 22. Retry-After

If an endpoint returns:

```text
429
```

or provides:

```text
Retry-After
```

Bezzo may honor the provider's retry guidance subject to configured safety limits.

A maliciously large delay must not create unbounded worker state.

---

# 23. Idempotency

Webhook consumers must assume duplicate delivery.

Bezzo outbound requests should include:

```text
X-Bezzo-Event-ID
```

and the event ID in the payload.

Consumers should maintain:

```text
processed_event(event_id)
```

or an equivalent idempotency record.

Inbound provider callbacks must also be deduplicated.

---

# 24. Duplicate Handling

Possible duplicate scenarios:

```text
delivery timeout
    ↓
consumer processed event
    ↓
response lost
    ↓
Bezzo retries
    ↓
consumer receives same event again
```

The consumer must recognize the event ID and return success without repeating the business operation.

---

# 25. Ordering Guarantees

Global ordering must not be assumed.

Bezzo should provide ordering within an `ordering_key` where required.

Examples:

```text
order:ord_123
supplier:sup_456
payment:pay_789
shipment:shp_111
```

Events with the same ordering key may be serialized.

Different ordering keys may execute concurrently.

This allows scalability without claiming impossible global ordering.

---

# 26. Ordering Implementation

A practical implementation can use partitioning by ordering key.

Example:

```text
hash(ordering_key)
       ↓
partition
       ↓
single ordered consumer lane
```

If strict ordering is not required for a specific event family, the system should not impose unnecessary serialization.

---

# 27. Dead-Letter Queue

Events that cannot be delivered after configured retries must enter a dead-letter state.

Dead-letter metadata should include:

- event ID
- endpoint
- subscription
- attempt count
- last status
- last error
- first failure
- final failure
- timestamps

Dead-letter events must remain recoverable.

---

# 28. Replay

Authorized operators must be able to replay:

- a single event
- a single endpoint delivery
- a selected time range
- a selected event type
- a selected subscription

Replay must create a new delivery attempt while preserving the original event ID.

The system must never mutate historical event data merely to make replay work.

---

# 29. Replay Safety

Replay must require:

- appropriate admin permission
- reason/comment
- audit record
- optional approval for high-risk integrations
- rate limiting

Bulk replay must be throttled.

Replay should support:

```text
dry run
preview
execute
```

where practical.

# 31. Endpoint Health

Bezzo should track:

- success rate
- failure rate
- timeout rate
- average latency
- p95 latency
- p99 latency
- recent 4xx rate
- recent 5xx rate
- retry volume
- dead-letter count

A persistently unhealthy endpoint may be automatically marked `DEGRADED` or `SUSPENDED` according to integration policy.

Automatic suspension must be reversible and observable.

---

# 32. Concurrency Limits

Each endpoint must have configurable concurrency limits.

Example:

```text
global webhook workers
       ↓
endpoint concurrency = N
```

One failing endpoint must not consume all delivery workers.

Supplier-specific and integration-specific quotas may also be applied.

---

# 33. Payload Limits

Outbound webhook payloads must have maximum size limits.

Large objects should not be embedded indefinitely.

Where appropriate:

```text
event payload
   +
resource reference
```

can be used.

Example:

```json
{
  "order_id": "ord_123",
  "resource_url": "...",
  "data_version": 1
}
```

Resource URLs must themselves be securely authorized.

---

# 34. Raw Payload Storage

For inbound webhooks, raw payloads may need to be stored for:

- dispute investigation
- provider debugging
- replay
- compliance evidence

Storage must use:

- encryption
- access controls
- retention limits
- sensitive-field redaction where possible

Payment secrets, authentication tokens, and unnecessary personal data must not be retained indefinitely.

---

# 35. Inbound Webhook Authentication

Inbound authentication depends on provider capability.

Supported approaches may include:

- HMAC signature
- asymmetric signature
- API key
- OAuth-based authentication
- provider IP allowlisting where reliable
- mTLS for high-security integrations

IP allowlisting must not be treated as a replacement for cryptographic verification when a provider supports signing.

---

# 36. Payment Gateway Webhooks

Payment webhooks are security-sensitive.

Bezzo must:

1. verify provider signature
2. validate event identity
3. validate payment/order mapping
4. deduplicate provider event IDs
5. persist the received event
6. update payment state through the payment state machine
7. create appropriate domain events
8. return acknowledgement quickly

Client-side payment success must never be the authoritative payment state.

---

# 37. Porter / Logistics Webhooks

Logistics callbacks may contain:

- shipment accepted
- driver assigned
- pickup started
- picked up
- in transit
- delivered
- cancelled
- failed
- proof-of-delivery references

Provider statuses must be mapped through the Bezzo logistics abstraction rather than leaking provider-specific states into the core domain.

---

# 38. ERP/POS Supplier Integrations

Supplier integrations may provide:

- inventory updates
- product updates
- pricing updates
- order acknowledgement
- fulfillment updates
- cancellation updates

Inbound data must pass through:

```text
authentication
→ schema validation
→ authorization
→ idempotency
→ normalization
→ business validation
→ domain update
→ event publication
```

Invalid supplier data must not directly corrupt core inventory state.

# 39. Inventory Integration Reliability

Inventory synchronization should tolerate:

- duplicate updates
- delayed updates
- out-of-order updates
- temporary ERP downtime
- partial synchronization
- malformed product records

Where supported, inventory updates should include:

- source timestamp
- source version
- source record ID
- supplier ID

Conflict resolution rules must be explicit.

# 40. Notification Provider Callbacks

Notification providers may return:

- delivered
- bounced
- failed
- rejected
- unsubscribed
- opened/read where supported

Provider callbacks must be mapped into normalized Bezzo communication events.

Provider-specific payloads should remain at the integration boundary.

# 41. External Provider Abstraction

External integrations should use adapter interfaces.

Example:

```ts
interface PaymentProviderAdapter {
  verifyWebhook(payload: Buffer, headers: Headers): Promise<WebhookVerification>;
  normalizeEvent(input: unknown): Promise<NormalizedPaymentEvent>;
}

interface LogisticsProviderAdapter {
  verifyWebhook(payload: Buffer, headers: Headers): Promise<WebhookVerification>;
  normalizeEvent(input: unknown): Promise<NormalizedLogisticsEvent>;
}
```

Core business modules should depend on normalized contracts, not provider SDK details.

The internal event bus should provide asynchronous communication between bounded modules.

# 43. Event Naming

Use stable names:

```text
<aggregate>.<past-tense-fact>
```

Examples:

```text

payment.paid
inventory.updated
shipment.delivered
```


# 44. Event Versioning

Events must be versioned.

Example:

```text
event_type = order.created
event_version = 1
```

Breaking schema changes should create a new version.

Examples:

```text
order.created v1
order.created v2
```

Do not silently change the meaning of existing fields.

---

# 45. Backward Compatibility

Consumers should be able to continue processing supported historical versions during migration.

Recommended strategy:

```text
producer
  ↓
supports v1 + v2
  ↓
consumers migrate
  ↓
v1 usage approaches zero
  ↓
v1 retirement window
  ↓
v1 removed
```

Version retirement must be announced and monitored.

- producer
- consumers
- payload schema

- optional fields
- compatibility rules

- retention
- example payload

# 48. Request Authentication and Authorization

Webhook delivery does not replace application-level authorization.

Before delivery:


# 49. Tenant Isolation

Every event containing tenant-specific information must carry sufficient ownership context internally.

Before sending:

```text

        ↓
```

Cross-tenant event delivery must be impossible through ordinary application paths.

- secrets

# 53. Distributed Tracing

Trace propagation should connect:

```text

 → database transaction
 → outbox event
 → dispatcher

```

External providers should not be trusted to preserve internal trace information, so Bezzo must maintain its own trace identity.

# 54. Alerting

Recommended alerts:

- rapidly increasing dead-letter count
- oldest pending event exceeds threshold
- webhook success rate drops
- endpoint timeout rate spikes
- payment webhook verification failures
- Porter callback failures
- ERP integration backlog
- outbox worker stopped
- queue consumer stopped
- replay volume unexpectedly high
- repeated signature failures
- abnormal webhook endpoint changes

Alerts must include actionable context.

---

# 55. Failure Modes

## Database unavailable

Do not acknowledge a business transaction that requires durable state unless the transaction can be safely committed.

## Outbox worker unavailable

Events remain pending and are processed when workers recover.

## Queue unavailable

Use the documented persistence boundary and recovery mechanism. Do not silently discard events.

## External endpoint unavailable

Retry with backoff and eventually dead-letter.

## Provider sends duplicate webhook

Deduplicate using provider event ID or a deterministic idempotency key.

## Provider sends malformed webhook

Reject safely, log sanitized diagnostics, and alert when volume is abnormal.

## Provider sends valid event out of order

Apply explicit provider/event ordering rules and ignore stale transitions when required.

---

# 56. Graceful Degradation

External webhook failure should not unnecessarily block:

- browsing
- search
- cart operations
- ordinary account access

For critical business transitions, the authoritative Bezzo state must be determined by core services and durable records.

External systems catch up asynchronously.

---

# 57. Circuit Breakers

External integrations should use circuit breakers where repeated failures indicate provider instability.

Conceptual states:

```text
CLOSED
  ↓ failures
OPEN
  ↓ cool-down
HALF_OPEN
  ├── success → CLOSED
  └── failure → OPEN
```

Circuit breakers prevent worker exhaustion and excessive provider traffic.

---

# 58. Rate Limits

Limits should exist at:

- global platform level
- integration level
- tenant level
- supplier level
- endpoint level
- event type level

Outbound webhook delivery must respect provider-specific published limits where applicable.

---

# 59. Provider Backpressure

If a provider begins returning:

```text
429
503
timeout
```

Bezzo should reduce concurrency for that provider/endpoint where appropriate.

This is preferable to continuing to increase traffic during an outage.

# 63. Replay Attack Protection

Signed webhook requests should contain a timestamp.

Consumers should reject requests outside a configured tolerance unless the provider uses a different replay-protection mechanism.

For sensitive inbound providers, maintain recent event IDs or equivalent replay state.

---

# 64. Endpoint Ownership Verification

Where feasible, endpoint ownership should be verified before activation.

Possible mechanisms:

- challenge endpoint
- verification token
- signed challenge
- provider registration flow

This reduces accidental or malicious subscription targeting.

# 70. Worker Safety

Workers must:

- use bounded concurrency
- claim jobs safely
- avoid double processing
- renew leases where required
- release failed jobs
- record attempts
- respect shutdown signals
- emit metrics

Graceful shutdown must prevent new work from being claimed while allowing active work to finish or safely return to the queue.

# 71. Exactly-Once Semantics

Bezzo should not claim universal exactly-once delivery.

The practical model is:

```text
at-least-once delivery
+
idempotent processing
+
deduplication
```

This provides reliable business behavior without requiring impossible guarantees across arbitrary external systems.

# 78. Operational Runbook: Webhook Failure

```text
1. Identify endpoint/integration
2. Inspect recent delivery attempts
3. Check provider health
4. Check latency and status distribution
5. Determine retryable vs permanent failure
6. Confirm endpoint configuration
7. Check signature/authentication failures
8. Check queue depth
9. Apply suspension/circuit breaker if necessary
10. Repair endpoint/provider issue
11. Resume delivery
12. Replay dead-lettered events if required
13. Verify successful recovery
14. Record incident
```

# 79. Operational Runbook: Payment Webhook Failure

```text
1. Detect callback failure
2. Preserve provider event ID
3. Check signature verification
4. Check payment/order mapping
5. Check duplicate state
6. Check gateway status
7. Retry provider-safe processing if required
8. Reconcile payment state
9. Update payment state machine
10. Verify customer/order consistency
11. Audit the resolution
```

# 80. Operational Runbook: Logistics Callback Failure

```text
1. Identify shipment
2. Identify provider event
3. Verify signature/authentication
4. Normalize provider state
5. Check current shipment state
6. Reject stale transition if required
7. Apply valid transition
8. Trigger customer notification
9. Reconcile with provider if state remains uncertain
```
